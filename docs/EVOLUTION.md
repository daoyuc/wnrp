## 二、各阶段的关键转折

### S0 雏形期：从「版本开关」长成「环境面板」

1. **PHP 版本的身份定为 FastCGI 端口**（ADR 01）：一个版本 = 一个端口 + 一个 `php-cgi` 进程，端口就是它在 `config.json` 里的唯一身份。此后「站点用哪个 PHP」=「`fastcgi_pass` 指向哪个端口」，端口同步、站点级换版本、反查映射全部建立在这个约定上。
2. **崩溃自愈搬到独立守护进程**（ADR 08）：放在 GUI 线程里，phpvm 自己崩了就无人救；改为独立进程 + 端口存活判定，才有了后来「看护列表跨重启裁剪」的基础。
3. **矛盾积累**：能力是一条条堆上去的（日志、托盘、Redis、扩展、下载装版），没有统一实现与测试，为 S3 的整顿埋下伏笔。

### S1 跨平台与建站闭环：从「改配置」到「建站点」

1. **运行期数据与程序文件分离**（ADR 06）：包目录只读（`.app` / `Program Files`）时自动改用 `~/.phpvm`，这一条同时是 S2「升级不丢配置」的前置条件。
2. **建站闭环成立**：6 套模板向导 + hosts 提权写入 + `nginx -t` + 平滑重载 + 失败回滚；随后补齐站点行级操作（启禁用 / 站点级换 PHP / 直达）与 hosts 的删除、备份、一键还原 —— 从此「写系统文件」这件事有了安全网（ADR 05、ADR 11）。
3. **i18n 全量包裹**（ADR 10）与**模块开关**（ADR 07）：前者让界面文案可译，后者让功能可停用（停用的模块不建页签、不 import 代码）。
4. **矛盾转移**：功能够了，但同一套流程在 CLI 与向导里各写一遍、备份逻辑散落各处 —— S3 直接对着这两点动刀。

### S2 分发与自维护：从「我的电脑」到「别人的电脑」

1. 单一版本号来源 + 发布资产命名 + SHA-256 校验 + 替换重启，配上 `packaging/build.py` 与 release workflow，形成可重复的发布链路。
2. 与 ADR 06 组合后达成「**升级替换程序文件、不动用户数据**」，这是自维护能力的分水岭。

### S3 工程化整顿：把「继续加功能」的成本压下去

1. **CLI 成为一等公民**（ADR 09、ADR 02）：`core/*` 不依赖 tkinter，CLI 与 GUI 共用同一实现；从此 AI / 脚本 / CI 有了唯一入口（契约见 [`../AGENTS.md`](../AGENTS.md)）。
2. **建站流程唯一化**：`core/site_service.py` 把「证书 → 写 vhost → 补 include → `nginx -t` → hosts → 重载 + 回滚」下沉为唯一实现，CLI 与向导的差异退化为显式开关。同理收敛 `core/file_backup.py`（写外部文件统一「备份 → 改 → 校验 → 失败回滚」）。
3. **测试与文档从 0 起步**：`tests/` 首次建立（35 例），随后建立文档体系与 ADR（ADR 12：可生成的部分不手写，如 `docs/CLI.md`）。
4. **两处「机制回退」值得记住**：ini 从双份（CLI / FastCGI 各一份）回退为**统一 `php.ini`**（ADR 03）；自动启动从「拉起全部版本」回退为**只拉版本号最新**（ADR 04）。两次都是「复杂机制带来的困惑 > 收益」，果断回退而不是继续打补丁。

### S4 调研驱动期：先对标，再立项

1. 竞品调研的结论是「差距不在装更多东西，而在**排障、调试、可见性**」，于是 P0 全部是**串联既有 core 能力**（体检诊断、Xdebug 开关、日志聚合），零新依赖。
2. 由此形成固定的推进顺序：**core 落地 → CLI 命令 → UI 入口 → 测试 → 文档/i18n**（ADR 02 的直接产物），后续每个功能都照此执行。
3. 副作用：密集落地把 i18n 欠账和测试的平台性失败同时放大 —— 这两笔账在 S5 集中还。

### S5 真机收敛期：把功能拉回「可交付」

1. **只在开发者机器上跑过 ≠ 真的能用**：Windows 上空 notebook `insert` 导致**启动必崩**、F12 资源监控因误用 `kernel32.GetProcessMemoryInfo` 而**完全失效**、F9 Adminer 生成含 Windows 反斜杠的坏 `root`、跨线程 `after()` 丢首屏 —— 全部是「只做只读冒烟」发现不了的问题。
2. **测试成为跨平台闸门**：补齐 `tests/test_main_window_smoke.py`（真建一次主窗口）并让三平台跑测试进 CI（此前 CI 只构建安装包，测试从不跑）。
3. **发现一类新缺陷：功能做完了，但没接进既有链路**（本次 `f3c1ba3` 即典型）：Adminer 选 PHP 时只调 `scan_versions()` 未刷新运行状态，把站点指向已停止的 PHP 版本 → 502；站点映射面板漏登记进统一刷新列表 → 新站点要手点刷新才出现。**能力本身没问题，接线不全。** 这类缺陷应作为新功能验收的固定检查项。

## 四、当前所处位置

1. **能力基线**：已从「PHP 版本开关」长出完整的本地环境面板 —— 建站闭环、排障诊断、调试、日志、备份迁移、邮件捕获、资源监控、CLI 自动化、分发升级。逐项落点见 [`MODULES.md`](MODULES.md)。
2. **已收敛的工程纪律**（新功能必须遵守，否则就是回退）：
   - `core/*` 不依赖 tkinter；CLI 与 GUI 共用同一实现（ADR 02）；
   - 写外部文件一律「备份 → 改 → 校验 → 失败回滚」（ADR 05），且只操作自己托管的东西（ADR 11）；
   - 后台操作走「线程 + queue + 主线程 drain」，禁止跨线程调用 tk；
   - 新能力按「core → CLI → UI → 测试 → 文档/i18n」顺序推进；
   - 文档按读者意图分层，可生成的部分不手写（ADR 12）。
3. **存量问题**（明细与背景见 [`../ROADMAP.md`](../ROADMAP.md)「已知存量问题」）：
   - i18n 欠账：en / zh_TW 各约 150 条、ja / ko 各约 385 条；且扫描脚本只扫 `ui/` 与 `core/`，漏掉 `cli.py`；
   - CI 已能在三平台跑测试，但 macOS / Ubuntu 两个 runner 尚未在实机之外验证过（首次跑红需先分辨是环境差异还是代码）；
   - P3 候选与 P2 剩余项（见下节）未动工；
   - macOS 托盘仍缺（GUI 已适配，托盘仅 Windows）。

## 五、下一步建议

排序依据沿用调研结论：**排障高频 > 复用既有 core > 不引入外部依赖/常驻进程 > 能形成差异点**。

| 优先级 | 方向 | 依据 | 成本 | 与 ROADMAP 的关系 | 验收要点 |
|---|---|---|---|---|---|
| 1 | **落地后一致性收口**：新能力必须接进既有状态刷新与统一实现链路 | S5 暴露的 Adminer 502 与站点映射不刷新，都是「功能做完了、接线不全」；同类风险随能力增加而累积 | S | 新增一条验收纪律，写入 ROADMAP「每阶段固定收尾」 | 新能力接入统一刷新登记；取 PHP 状态一律走 `scan_versions + resolve`；不出现「报成功但不可用」 |
| 2 | **i18n 欠账集中清理**（含补扫 `cli.py`） | 四语言长期缺译，且 CLI 新增文案不在统计内，欠账只会滚雪球 | M | ROADMAP 已登记为存量问题 | 每轮只保证「新增文案 0 缺失」；另开一轮集中补历史欠账 |
| 3 | **CI 三平台首跑验证** | 测试已在三平台配置，但从未在实机之外跑通，红/绿都不可信 | S | 已建 `.github/workflows/tests.yml` | 三平台全绿；失败先判定是环境差异还是代码 |
| 4 | **F13 多 server 块逐块编辑** | 用户 vhost 里确有同文件多 server 块时才做；`core/nginx_conf.py` 已有块解析能力 | M | ROADMAP P3 候选 | 先做只读解析与逐块列表，落盘动作沿用「备份 + `nginx -t` + 回滚」 |
| 5 | **F14 目录停靠 park / F10 Node 多版本** | 触发条件未到（没人抱怨「新项目都要走一遍向导」/ 前端构建撞 Node 版本） | M–L | 调研 P2，按需启动 | 各先做「预览清单 / 显示已装版本」的只读版本，不落盘、不下载 |
| 6 | **F8 项目级配置深化** | 已落地基础版（`.phpvm.json` 读取 + apply），等真实诉求再扩展 | M | 调研 P2 | 出现「多项目切换 / 团队一致」诉求时再加环境变量与服务编排 |

**暂不建议**：macOS 菜单栏托盘（纯标准库实现成本高，已有「重启 / 状态栏」入口替代）；邮件捕获改为常驻服务（当前随 phpvm 进程运行，界面已明确提示，若需常驻可参照 `core/crash_watchdog.py` 的独立守护模式）。

## 六、明确不做

以下为调研阶段即已否决、写下来避免反复讨论的方向：

- **Docker 化 / 容器编排** —— 与「零依赖、原生进程直管」定位冲突，要容器的用户会直接选 DDEV；
- **内置 IDE / 代码编辑器** —— 与工具定位无关，体积与维护成本巨大；
- **账号体系 / 云同步 / 团队协作** —— 本地单机工具的边界，引入服务端即改变产品性质；
- **外网穿透分享（ngrok 类）** —— 依赖第三方账号与网络，故障不可控；
- **DNS 泛解析（dnsmasq / Windows 第三方）** —— 跨平台成本高、权限敏感，hosts 标记块已覆盖绝大多数场景；
- **数据库数据备份（datadir 打包）** —— 体积大且可能正在写入，只备份配置，数据用官方工具导出；
- **安装更多运行时（Java / Go / Python 全家桶）** —— 会稀释「PHP 环境」定位。

## 七、维护约定

出现下列任一情况，**同轮更新本文档**：

1. 发生**架构级转折**（新增层、改变线程/进程模型、改变持久化落点、机制回退）—— 补一节「关键转折」并链到新增的 ADR；
2. 阶段矛盾发生迁移（例如从「加功能」转入「真机收敛」）—— 调整第一节的阶段划分；
3. 第三节「能力演进曲线」出现新的能力域 —— 补一行；
4. 第五节的候选方向立项或完成 —— 更新优先级表，并在 [`../ROADMAP.md`](../ROADMAP.md) 登记本轮。

改完跑一次：`python3.13 -m unittest tests.test_docs`（链接可达、引用的代码路径存在、表格列数一致）。
